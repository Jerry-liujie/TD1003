\chapter{Background}
\label{chap:background}

This chapter provides the shared foundation for the rest of the
dissertation: the query rewriting problem, SQL pipelines and the
extension of rewriting to them, the rule-based paradigm that has
dominated automatic rewriting, the techniques available for
establishing that two queries are equivalent, and the two tools this
dissertation builds on, program synthesis and large language models.
Readers familiar with these topics can skim this chapter and refer
back to it as needed.

\section{The Query Rewriting Problem}
\label{sec:bg:problem}

Throughout this dissertation, a query $q$ is a SQL \texttt{SELECT}
statement over a database whose schema and integrity constraints are
known. Two queries $q$ and $q'$ are \emph{semantically equivalent},
written $q \equiv q'$, if they produce identical results on every
database instance that satisfies those constraints. Identical is meant
under SQL's bag semantics: the same rows with the same multiplicities
(and, for queries whose results are explicitly ordered, in the same
order). The constraints are part of the definition for a practical
reason: many valuable rewrites are correct only because of them. A
rewrite that drops a duplicate-eliminating step, for example, may be
justified by a key constraint and incorrect without it.

The \emph{query rewriting problem} is then: given $q$, find a query
$q'$ such that $q' \equiv q$ and $q'$ executes at lower cost, where
cost means wall-clock latency and, in cloud settings, the money
charged for the computation.

To see where rewriting fits, consider how a database processes a
query. The optimizer first translates the SQL statement into an
\emph{execution plan}, a tree of physical operators such as scans,
joins, and aggregations. Among the many plans that could implement
the given query, it selects the one its internal cost estimates deem
cheapest, and the engine then executes that plan. Most systems
display the selected plan through commands such as \texttt{EXPLAIN},
and the plan shows how the work is distributed across operators;
Chapter~4 relies on this visibility, inspecting a query's plan to
identify its performance bottleneck, the operators where most of the
time is spent.

Optimizers are not limited to plan selection. Most also restructure
the query itself to a degree, applying transformations such as
predicate pushdown and subquery unnesting before and during plan
search. But every transformation an engine applies, at the plan
level or the SQL level, comes from a fixed repertoire that its
developers anticipated, implemented, and shipped. When two
equivalent queries differ in a way that lies outside this
repertoire, the engine optimizes them to very different plans, and
such pairs are common in practice: their running times on the same
engine can differ by orders of magnitude, and every speedup reported
in Chapters~3 through~5 comes, by construction, from a
transformation the underlying engine did not perform on its own.
Query rewriting addresses this gap from outside the engine: it
transforms the SQL before the optimizer sees it, and its output is
ordinary SQL handed to the optimizer like any other query, so
rewriting complements the optimizer rather than replacing it, and
its benefits carry to any engine. One might object that any missing
transformation could simply be added to the engine as one more
rule. That is precisely the rule-based paradigm, and
Section~\ref{sec:bg:rules} examines both its successes and the
structural limits that motivate this dissertation.

Solving the rewriting problem also requires judging cost, which is
itself nontrivial. A query's cost can be judged in three ways: by
executing the query and measuring, which is accurate but expensive;
by asking the engine for an estimate, since the optimizer attaches
its internal cost estimates to the plan it selects, and cloud
warehouses likewise estimate the resources a query will consume
before running it; or by building a dedicated \emph{cost model} that
predicts cost from the query's structure and statistics about the
data, possibly learned from past executions, as the learned cost
model in Chapter~5 does. All three appear in this dissertation.

Whichever technique performs it, rewriting has a price of its own:
search time, verification time, or calls to a commercial language
model. The investment pays off for queries that are executed
repeatedly, where a one-time improvement is harvested on every
subsequent run. Such recurring, resource-intensive queries dominate
production analytics
workloads~\cite{jindal2018selecting,dbtcasestudy1,dbtcasestudy2}, and
they are the setting this dissertation assumes throughout.

\section{SQL Pipelines}
\label{sec:bg:pipelines}

Recurrence at organizational scale takes the form of the \emph{SQL
pipeline}. In tools such as dbt~\cite{dbtWhatExactly}, an
organization's transformation logic is decomposed into SQL
transformations (called \emph{models} in dbt), each defined by a
single \texttt{SELECT} statement, and each transformation declares
which source tables and which other transformations it reads from.
These declarations make the dependencies explicit, so the pipeline
forms a directed acyclic graph: nodes are SQL transformations, and an
edge records that one transformation consumes another's output. An
orchestrator re-executes the pipeline on a schedule, materializing
each node's result as a table or view that downstream nodes,
dashboards, and applications then read. The scale of these pipelines
in production is substantial. Statistics shared by dbt indicate that
five percent of dbt projects, more than a thousand of them, contain
over five thousand models, and Siemens has reported operating more
than 85{,}000 models across 800 dbt projects, with 2{,}500 jobs
executing daily~\cite{dengsoe2023large}. Pipelines of this size are
not written once; they evolve for years with the organizations that
maintain them.

Pipelines enlarge the rewriting problem. The object being rewritten
is now the pipeline itself: individual transformations may be
rewritten as before, but logic may also be moved across nodes, for
example by inlining part of a producer into its consumers or pulling
a predicate from a consumer into a producer; nodes may be split,
merged, added, or removed; and decisions about what to materialize
and how often to refresh become part of the optimization. What must
be preserved also changes. Correctness no longer means preserving
each node's output; it means preserving the pipeline's \emph{final
outputs}, the results that external consumers actually read.
Internal nodes may change or disappear so long as the outputs at the
boundary are unchanged.

In principle, pipeline rewriting reduces to query rewriting. Because
every transformation is itself a \texttt{SELECT} statement, any
final output of a pipeline can be unfolded into a single
self-contained query: substitute each referenced transformation with
its defining statement, and repeat until only source tables remain.
In this sense a pipeline is, semantically, a collection of large
queries, one per final output, and pipeline equivalence is exactly
query equivalence applied to each of them. This reduction supplies
the correctness criterion stated above. As a representation for
optimization, however, the unfolded query discards precisely the
structure that matters. First, it hides sharing: a transformation
read by several outputs reappears as duplicated logic inside each
unfolded query, so the central pipeline-level question, namely what
to compute once, persist, and reuse across consumers, cannot even be
posed within any single query. Second, it collapses time: a pipeline
persists intermediate results across runs and refreshes different
nodes at different frequencies, while a query describes one
execution and has no notion of persistent intermediate state or of
parts running on different schedules. Third, it fails at scale:
unfolding a real project produces deeply nested SQL with tens or
hundreds of layers, far beyond what today's optimizers, rewriters,
or equivalence checkers can process, and since the engine optimizes
each statement in isolation, materialization boundaries are walls
its optimizer cannot see across in any case. The dependency graph is
therefore not incidental packaging around one large query; it is the
representation that keeps sharing, persistence, and refresh
explicit, and those are exactly the dimensions in which
pipeline-level optimization lives. Chapter~5 builds directly on this
structure.

\section{Rule-Based Query Rewriting}
\label{sec:bg:rules}

Section~\ref{sec:bg:problem} ended at the rule-based paradigm; this
section examines it. A rewrite rule consists of a syntactic pattern,
a condition under which the transformation is safe, and a
replacement. Classical rules include pushing filtering predicates
closer to the data they filter~\cite{levy1994query}, unnesting
nested subqueries into joins~\cite{kim1982optimizing}, and
eliminating redundant joins or duplicate-removal steps that
constraints render unnecessary. A rule engine applies its rules to
the query's relational algebra representation: it walks the operator
tree, finds fragments that match a rule's pattern, checks the rule's
condition against the schema and constraints, and performs the
replacement, either in a dedicated rewrite phase run before plan
selection, the architecture that Starburst
introduced~\cite{pirahesh1992extensible}, or interleaved with
cost-based plan search so that a rewrite is kept only when it leads
to a cheaper plan. Apache Calcite~\cite{begoli2018apache}, the
open-source optimizer embedded in many data systems, is the
contemporary embodiment: a manually curated rule set, accumulated
and refined over years, applied through exactly this machinery.

Rules have earned their dominance: every major database runs a
rewrite phase over every query it executes. WeTune~\cite{wetune}
measured how far such rule sets reach by studying 50 real-world
rewrite requests drawn from popular open-source applications. The
rules of Microsoft SQL Server, accumulated over decades of
commercial development, resolved nearly half of them, a testament to
how much value rules deliver in practice. The same study also
exposed the paradigm's limits: Calcite's rules covered only 4 of the
50 requests, and WeTune's automatic enumeration discovered more than
a thousand promising rules absent from existing systems, resolving
38 of the requests with them. Even the most mature rule sets, then,
are far from complete.

The obvious response, adding more rules, is harder than it sounds,
and a deeper reason is that rules interact. A rule's benefit is not
a fixed property of the rule itself: applying one rule changes which
other rules match, so what a rule contributes depends on which rules
surround it and in what order they fire, and the same rule can
unlock a large improvement in one sequence while degrading
performance in another. This has two consequences. Even with a fixed
rule set, deciding which rules to apply and in what order is a
search problem in its own right, which LearnedRewrite~\cite{LR}
addresses by learning application orders under the guidance of a
cost model. And every extension compounds the problem: a new rule
must be proven safe on its own, which already demands rare
expertise, yet its value can only be judged in combination with the
rules already present, whose behavior it in turn perturbs. Rule sets
therefore grow slowly while coverage gaps persist. The chapters that
follow use Calcite and LearnedRewrite as rule-based baselines, and
take the other route: producing rewrites without rules at all.

\section{Establishing Query Equivalence}
\label{sec:bg:equivalence}

Every rewriting technique in this dissertation must answer the same
question: is the candidate $q'$ really equivalent to $q$? For
rule-based systems the question is settled once per rule, when the
rule is proven. A system that generates rewrites freely must instead
settle it once per candidate, which makes equivalence checking part
of the rewriting process itself. The question is also fundamentally
hard. For queries expressible in the relational calculus, the formal
core of SQL, equivalence over finite databases is undecidable: by
Trakhtenbrot's theorem, no algorithm can decide whether a
first-order sentence is satisfiable on some finite database, and
query equivalence inherits this
impossibility~\cite{trakhtenbrot1950,abiteboul1995foundations}. The
difficulty persists under severe restriction: even for conjunctive
queries, plain select-project-join queries without negation or
aggregation, equivalence is NP-complete~\cite{chandra1977optimal}.
Practical systems therefore combine several techniques, trading
coverage, cost, and strength of assurance against one another. The
rest of this section describes each technique together with what it
can realistically deliver today.

\emph{Testing} executes both queries on concrete database instances
and compares their results. A single mismatching instance is a
\emph{counterexample} that definitively refutes equivalence, and a
counterexample is useful beyond refutation: it can steer a search
away from a mistaken region, or show a language model precisely how
its suggestion fails. Agreement on all tested instances proves
nothing about untested ones, so testing is an incomplete filter, but
it is also the most general tier: it applies to essentially any SQL
the engine can execute, including features far beyond what any
verifier supports. Its effectiveness depends on the test data.
Random data rarely exposes subtle differences, and systematic test
generation for expressive SQL had received little attention;
Chapter~3 develops a tester that analyzes the two queries' filter
conditions, groupings, and duplicate handling to construct small
databases likely to expose a difference, and Chapter~4 adopts the
same tester.

\emph{Bounded verification} proves two queries equivalent on all
database instances up to a size bound, typically by encoding the
check as constraints for an SMT solver; the guarantee is exhaustive
below the bound and silent above it. This dissertation uses the
bounded verifiers of Cosette~\cite{chu2017cosette,wang2018speeding},
with the bound in Chapter~3 set to two rows per input table and
cell values left unconstrained. More recently,
VeriEQL~\cite{he2024verieql} has pushed this tier to the most
expressive SQL supported by any equivalence checker to date,
handling features such as sorting, \texttt{CASE} expressions, and
rich integrity constraints, and generating counterexamples that
have exposed real bugs in MySQL and Calcite. Bounded assurance is
meaningful in practice because inequivalent query pairs are
overwhelmingly likely to differ already on small instances, an
assumption borne out empirically in Chapter~3.

\emph{Full verification} aims at unconditional proofs. A line of
provers has steadily expanded what is provable, from
Cosette~\cite{chu2017cosette} through algebraic
approaches~\cite{chu2018axiomatic} and symbolic
reasoning~\cite{zhou2022spes} to SQLSolver~\cite{ding2023proving},
which proves 346 of 359 equivalent query pairs derived from the
rewrite rules of Calcite and Spark SQL. That result calibrates
expectations in both directions. Rule-sized, well-structured query
pairs are now largely within reach of automated proof; at the same
time, full analytic queries, with window functions, deeply nested
correlated subqueries, and vendor-specific constructs, routinely
fall outside the supported fragments, and on such inputs a verifier
returns unknown rather than a verdict. This is why practical
systems layer the tiers, spending cheap tests first and reserving
expensive proofs for the candidates that survive and that the
verifier can accept.

At pipeline scale, formal proof is out of reach entirely: a
refactoring may touch dozens of interdependent transformations, and
existing verifiers support neither the SQL features nor the
multi-statement scope involved. \emph{Data-backed checking} takes
the pragmatic point on the spectrum: execute the original and
refactored pipelines on production-scale data and compare the
materialized outputs that external consumers read. The resulting
assurance is relative to the data tested rather than universal, but
it concerns exactly the outputs the organization depends on, on
exactly the data it runs.

The three systems in this dissertation each assemble their
assurance from these tiers. SlabCity (Chapter~3) layers testing
beneath bounded and full verification inside its search loop.
GenRewrite (Chapter~4) attempts full verification first; because
the complex analytic queries it targets often come back unknown, it
falls back to testing, which in that setting is the more practical
instrument, and it turns the counterexamples testing produces into
corrections. DAGSmith (Chapter~5) admits a pipeline refactoring
only after data-backed checking confirms its final outputs.

\section{Program Synthesis and Large Language Models}
\label{sec:bg:tools}

Moving beyond rules requires a source of rewrites that no one wrote
down in advance. This dissertation draws on two, and both have
earned their place.

\emph{Program synthesis} is the task of automatically finding a
program, within a defined space, that satisfies a specification. It
is a mature field with a real-world track record: synthesis ships
inside mainstream products, most famously FlashFill, which
synthesizes spreadsheet transformations from a few examples within
Microsoft Excel~\cite{gulwani2011automating}, and its algorithmic
toolkit is well developed~\cite{gulwani2017program}. Its defining
strength for our purposes is systematic coverage with correctness
built in: a synthesizer explores its space exhaustively up to
resource limits, misses nothing that the space can express, and
pairs naturally with the checking of
Section~\ref{sec:bg:equivalence}, since every candidate it emits can
be tested and verified. Query rewriting instantiates synthesis
naturally: the space is SQL, and the specification is the original
query itself, since the synthesized program must be equivalent to it
and faster. The central challenge is scale, as the candidate space
grows explosively with program size; practical synthesizers respond
with aggressive pruning, discarding whole families of candidates at
once, and with feedback loops such as counterexample-guided
inductive synthesis, in which each failed candidate's counterexample
sharpens the tests that future candidates must
pass~\cite{solar2008program}. Synthesis has been applied to SQL
chiefly to generate queries from input-output
examples~\cite{wang2017synthesizing}; using it to optimize an
existing query is the step Chapter~3 takes.

\emph{Large language models} are neural networks trained on vast
corpora of text and code to predict the next token, a simple
objective that at sufficient scale yields broad competence in
understanding and generating programs~\cite{zhao2023llm}. Their rise
has been the defining development of recent software practice, and
their fit for SQL is specific, not incidental. Trained on decades of
public code, documentation, and technical discussion, they carry the
accumulated experience of how practitioners write and reshape
queries across dialects, they operate directly on the messy,
sprawling SQL of real applications that formal tools cannot even
parse, and they are as fluent in natural language as in code, able
to explain a transformation as readily as perform it, an ability
Chapter~4 turns into a mechanism. They are used through
\emph{prompting}, a task description supplied as input
text~\cite{googleprompt}, with costs metered in
\emph{tokens}~\cite{openaitokens}, so the number and length of model
calls is an engineering concern. Their limitation is equally clear:
a model's output is fluent and confident but carries no guarantee of
correctness, a failure mode commonly called hallucination, and a
model has no innate sense of whether a rewrite is faster. Neither
weakness is disqualifying. Both are managed by construction in this
dissertation, which pairs every model suggestion with the
independent checking of Section~\ref{sec:bg:equivalence} and with
measured performance evaluation.

There is a further reason these tools belong in this dissertation:
they are reshaping what there is to optimize. A growing share of SQL
is now written by language models themselves, through AI-assisted
development and natural language interfaces to
data~\cite{dbt2025state}, and that share is rising. This changes the
optimization problem structurally. A model generates a query to
capture intent, with no visibility into the data's statistics, the
engine's characteristics, or the cost of its syntactic choices, so
the inefficiencies of generated SQL are systematic rather than
accidental, and they are produced at machine speed, far beyond what
manual tuning can absorb. The plausible future is a toolchain in
which generation and optimization are separate passes: models write
SQL that captures intent, and automatic rewriting, disciplined by
verification, makes that SQL efficient, with the knowledge distilled
from successful rewrites flowing back to improve generation itself.
This dissertation builds that second pass.

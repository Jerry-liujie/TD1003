\section{Motivating Examples}
\label{slab:sec:motivating-example}

Chapter~2 made an abstract claim: rule-based rewriting is bounded by
its rule set. This section makes the claim concrete. It walks through
four queries, drawn from two sources also used in our evaluation
(\cref{slab:sec:eval}): solutions written by real developers on
LeetCode, and test queries from the Apache Calcite
project~\cite{calcite}. For each, we show the rewrite \slabcity
finds, and examine why encoding that rewrite as a rule would be
somewhere between painful and hopeless.

\head{Example 1. Restructuring around window functions}
LeetCode problem \#1308 asks, over a table \texttt{scores} with
columns \texttt{(gender,day,score)} and primary key
\texttt{(gender,day)}, for the running total score of each gender on
each day. $\query_1$ in Table~\ref{slab:tab:Q1-Q2} is a
participant-written solution; $\query_2$ is what \slabcity produces
from it. On a randomly populated database of one million rows,
$\query_2$ runs more than 2000x faster. 

\begin{table}[!t]
\footnotesize
\caption{$\query_1$ is human-written. $\query_2$ is generated by $\slabcity$.}
\vspace{-5pt}
\begin{tabular}{|c|c|}
\hline
 $\query_1$

 & 
 
 \makecell[l]{\sqlselectcolor \  \sqldistinctcolor s1.gender, s1.day, \sqlsumcolor(s2.score)\\
              \sqlfromcolor scores \sqlascolor s1 \sqljoincolor scores \sqlascolor s2 \\
              \hspace{2em} \sqloncolor s1.gender = s2.gender\\
              \sqlwherecolor s2.day <= s1.day \\
              $\sqlgroupbycolor$ s1.gender, s1.day
              }  
\\
\hline
$\query_2$
&
 \makecell[l]{ \sqlselectcolor gender, day, \\ \hspace{1em} \sqlsumcolor(score) \sqlovercolor (\sqlpartitionbycolor gender \sqlorderbycolor day) \\
 \sqlfromcolor scores}
  \\
 \hline
\end{tabular}
% \vspace{5pt}

\vspace{-5pt}
\label{slab:tab:Q1-Q2}
\end{table}



Two defects make $\query_1$ slow. It computes the running total
through a self-join, materializing a huge intermediate result where a
window function computes the same total in a single pass. And its
\sqldistinctcolor is dead weight: \texttt{(gender,day)} is the
primary key, so duplicates cannot arise. Repairing either defect by
rule is awkward, because the repair is not local: getting from
$\query_1$ to $\query_2$ changes nearly every clause of the query, so
no rule that matches and replaces a fragment of $\query_1$ can express
it, and a rule matching the whole shape of $\query_1$ would need to
anticipate this exact pattern, along with the side conditions
guaranteeing its correctness. Anticipating every such pattern in
advance is the losing game that Chapter~2 described. \slabcity plays a
different game: it searches the query language itself (defined in
Figure~\ref{slab:fig:querysyntax}) for equivalent formulations, so a
rewrite that shares almost no syntax with the input is as reachable as
a local patch. Neither {\learnedrewrite} (\LR)~\cite{LR} nor
{\wetune} (\WT)~\cite{wetune}, the state-of-the-art rule-based
rewriters we evaluate in \cref{slab:sec:eval}, is able to optimize
$\query_1$ at all.

%Capturing this kind of rewrite for rule-based techniques is inherently difficult as their ability to exploit integrity constraints is rather weak. For example, they are comfortable with checking if a single column is primary key so that a specific rule can be applied but they cannot infer if a single column (not primary key) is unique given a set of integrity constraints, which requires reasoning ability. As a result, syntactic pattern matching needs to be used more heavily to make up for their weak constraint checking, which is error-prone and still incomplete. In contrast, since \slabcity is not restricted to rules, as long as there is an optimal query in the search space, it will eventually find it.


The inefficiency in $\query_3$ is a window function with
$\sqlpartitionbycolor$ that the constraints render pointless. Because
\texttt{(cid,year)} is the primary key, fixing \texttt{year} leaves
at most one row per \texttt{cid}, so partitioning by
\texttt{(cid,year)} and grouping by \texttt{cid} coincide once the
year is pinned to 2021; $\query'_4$ exploits this to replace the
window function with plain aggregation and $\sqlgroupbycolor$.
Pushing the same reasoning one step further, the key also functionally
determines \texttt{revenue}, so even the aggregation is unnecessary,
which is the rewrite $\query_4$ embodies. Neither \LR nor \WT can
rewrite $\query_3$ into anything. The obstacle is that rule engines
consult integrity constraints only through narrow, hard-coded side
conditions attached to patterns; deriving consequences of a constraint
set, such as the uniqueness of a non-key column in a filtered context,
is inference, not pattern matching. \slabcity does not need the
inference to be anticipated: if a better query exists in the search
space, the search can reach it. 



\head{Example 3. Eliminating a redundant self-join}
Calcite ships a test suite for its rewrite rules, and $\query_5$ in
Table~\ref{slab:tab:Q5-Q7} is one of its cases
(``testPushAggregateThroughOuterJoin14''), over a table \texttt{emp}
with columns \texttt{(empno,ename,mgr)} and primary key
\texttt{empno}. $\query_5$ self-joins \texttt{emp} on the
\texttt{mgr} column and groups by the join key, which amounts to
selecting distinct values with \sqldistinctcolor. Calcite's own rules
rewrite $\query_5$ into $\query_6$, pushing the grouping below the
join to shrink its operands; that yields a 926x speedup on a database
with 4M rows. \slabcity instead produces $\query_7$, which is 1833x
faster than $\query_5$ on the same data, because the self-join can be
removed entirely rather than merely made cheaper.

$\query_7$ is \slabcity's output.}
\vspace{-8pt}

 \hline
 $\query_5$ 

 & 
 
 \makecell[l]{\sqlselectcolor e0.mgr \sqlascolor mgr0, e1.mgr \sqlascolor mgr1 \\
             \sqlfromcolor emp \sqlascolor e0 \sqlfulljoincolor emp \sqlascolor e1 \sqloncolor e0.mgr = e1.mgr\\
              $\sqlgroupbycolor$ e0.mgr, e1.mgr
              }  
\\

\hline

 $\query_6$ 

 &

            \hspace{1em} \sqlfulljoincolor (\sqlselectcolor mgr \sqlfromcolor emp $\sqlgroupbycolor$ mgr)  \sqlascolor e1 \\

              }  
\\

\hline

 $\query_7$ 

&

 \makecell[l]{\sqlselectcolor mgr \sqlascolor mgr0, mgr \sqlascolor mgr1 \\

No state-of-the-art rule-based rewriter finds $\query_7$:
\learnedrewrite reaches $\query_6$ and stops, and \wetune cannot
rewrite $\query_5$ at all. Recognizing the opportunity requires the
semantic fact that the two join operands are the same relation, and
self-join identity resists syntactic capture. A rule keyed to the
literal pattern\\
\texttt{\sqlfromcolor T AS T1 \sqljoincolor T AS T2}\\
misses the same join written\\
\texttt{\sqlfromcolor T AS T1 \sqljoincolor (\sqlselectcolor * from T) AS T2} \\
and every further disguise needs another pattern. For a search over
the query space, no recognition is required: the join-free $\query_7$
is simply a candidate, and it wins on both equivalence and speed.

\head{Example 4. Deduplicating set operations}
$\query_8$ in Table~\ref{slab:tab:Q8-Q10} is another Calcite test
case (``testPushMinThroughUnion''). Calcite's rules rewrite it into
$\query_9$ by pushing $\sqlgroupbycolor$ past $\sqlunionallcolor$,
moving latency by only about 2\% in either direction. \slabcity
rewrites it into $\query_{10}$, which is 1.7x faster, by exploiting
what the rules cannot see: the two sides of the $\sqlunionallcolor$
are identical, so the duplicated computation can be eliminated.
Neither \learnedrewrite (which reaches only $\query_9$) nor \wetune
(which produces nothing at all) finds this.

\head{Discussion}
Two terms are worth fixing, since the evaluation relies on them: a
technique \emph{rewrites} an input if it produces some equivalent
output query, and \emph{optimizes} it if the output is actually
faster; optimizing is the harder task. The examples above were chosen
because they are legible, but they are not isolated:
\cref{slab:sec:q1-coverage} reports many queries that current
rule-based systems cannot optimize, or cannot even rewrite, while
\slabcity can, and \cref{slab:sec:q2-reduction} shows that even where
both succeed, \slabcity's outputs are often substantially faster. The
pattern behind all four examples is the same. Each missed rewrite is
missed because some human would have had to foresee it as a rule and
encode its correctness conditions; a search over the query language
forgoes foresight, and finds what is there.
